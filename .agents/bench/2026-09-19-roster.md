## Tonight's decision: gpt-oss:20b isolated retest is blocked, not skipped

Per the task's own instruction, gpt-oss:20b needed a retest "FIRST and ALONE
in a throwaway `ollama serve` on port 11435" before trusting it near anything
else. Attempted exactly that:

```
OLLAMA_HOST=127.0.0.1:11435 OLLAMA_MODELS=/var/lib/ollama/models ollama serve
-> Error: mkdir /var/lib/ollama: file exists: ensure path elements are traversable
```

`ollama.service` runs as a dedicated `ollama` system user (confirmed via
`systemctl show ollama.service -p User -p Group` -> `User=ollama Group=ollama`),
and `/var/lib/ollama/models` is not world-readable. A throwaway instance
launched as `cryptix` genuinely cannot read the already-pulled model blobs
without either `sudo` (explicitly forbidden tonight) or a system-level
permission/group change (also out of scope — that's a NixOS module edit +
switch, and this session cannot switch). **This is a real blocker, not a
convenience skip** — logged in `BLOCKERS.md`.

**Consequence**: `gpt-oss:20b` and `devstral:24b` remain **unverified** under
the current roster/config. `ai-workstation.nix`'s model choices are
untouched tonight (per the task's own instruction: "Leave ai-workstation.nix's
model choices alone unless the data is unambiguous" — the data is not just
ambiguous, it's uncollectable right now). Whoever re-runs this needs either a
`sudo`-run throwaway instance, or (better, permanent fix) a home-manager/NixOS
change making `/var/lib/ollama/models` group-readable for a `cryptix`-joined
group, which is itself worth proposing as a follow-up so this isolation

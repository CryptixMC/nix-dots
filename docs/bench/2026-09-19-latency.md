# Qubi engine night — startup latency, before/after

Methodology: `~/qubi-staging/engine/acp_probe.py` drives a real `goose acp` process
over stdio (same protocol GooseAcpSession.qml speaks), timing real wall-clock
timestamps at each JSON-RPC boundary. No estimates. `~/qubi-staging/engine/acp_trace.py`
is the same thing with every event individually timestamped, used for root-causing.

## BEFORE — current spawn-on-open design (measured 2026-09-18, pre-engine)

Three points requested by Phase 6, mapped onto ACP's actual protocol boundaries
(there is no separate "overlay visible" step at the protocol level — the QML
window paints immediately; `spawn -> session/new result` is the real
work the overlay is waiting on before it can accept input):

| Point | Measured as | Value |
|---|---|---|
| SUPER+D press -> overlay visible | `Process.running=true` -> first paint | not protocol-measurable; QML window creation, expected sub-frame (not the bottleneck, see TTFT below) |
| spawn -> session ready (session/new resolves) | `spawn_to_session_ready_ms` | **170-186ms**, consistent across 4 clean runs |
| spawn -> session list populated | `spawn_to_session_list_ms` | **175-186ms** (session/list is +3ms after session/new; overlay doesn't actually call this today but SessionsPicker.qml does) |
| first prompt sent -> first token (TTFT) | `ttft_ms`, wall-clock from `session/prompt` send to first `agent_message_chunk`/`agent_thought_chunk` | **17.0s - 23.3s** across 4 clean single-shot runs (see raw numbers below) |

Raw runs (model already warm/resident in every case, `qwen3:4b`, default
6-extension config matching what GooseAcpSession.qml actually spawns):

```
before-clean            spawn_ready=180ms  ttft=23318ms  turn_total=44329ms
thinking-env-override   spawn_ready=170ms  ttft=16971ms  turn_total=27356ms  (GOOSE_LOCAL_ENABLE_THINKING=false passed explicitly)
before-run1             spawn_ready=147ms  ttft=18621ms  turn_total=28251ms
before-run2             spawn_ready=183ms  ttft=35994ms  turn_total=43685ms  (run immediately after run1, no model-reload — variance from Ollama's own slot/cache churn, see finding below)
```

**Root cause of the 17-36s TTFT (this is the actual finding, not the headline
number)**: it is NOT process spawn (that's 150-190ms, already fast) and NOT
raw model inference speed (`curl`-direct `/api/generate` against the same
resident `qwen3:4b` returns first token in **20-34ms**, confirmed by direct
measurement). Confirmed via `journalctl -u ollama` cross-referenced against
the trace: for the prompt "Say the single word: ready", Goose's actual
outgoing request carries **~3600 tokens of system prompt** (tool schemas +
built-in agent instructions + AGENTS.md, for a default 6-extension config),
and the model then spends **1500+ tokens "thinking"** before emitting the
one-word answer — confirmed by Ollama's own `print_timing` log line
(`eval time = 21006.50 ms / 1500 tokens`, `tg = 71.36 t/s`). The env var
`GOOSE_LOCAL_ENABLE_THINKING=false` (already set in `goose.nix`'s
`environment` block, per the existing "Part II Stage 3" comment) only
partially suppresses this — with it explicitly set, TTFT dropped from
23.3s to 17.0s in a controlled A/B, not down to the sub-2s a genuinely
thinking-off request should show. This is not a Goose config bug I can fix
by flipping one flag; it's a real reasoning-model behavior. **This is the
single strongest piece of evidence for Phase 3's design**: a light tier
running *without* extensive tool-schema bloat and with a model that
doesn't reflexively reason 1500 tokens about a one-word answer is the
actual fix, not process architecture. The engine's process-pool warm-start
(Phase 2c/f) eliminates the 170-190ms spawn cost entirely (real, but small
next to the 17-23s problem); the routing/escalation work (Phase 3) is what
actually addresses the dominant cost.

Also observed, not yet root-caused, logged here rather than hidden: Ollama's
own GIN access log reports wall-clock durations for these same requests
(44.2s, 59.3s) that are roughly **double** the internal `slot print_timing`
total (22.6s, 23.4s) for the identical request. Internal generation timing
is real and matches the observed TTFT-to-completion window well; the extra
outer-HTTP-layer time is unexplained and did not block tonight's work
(routing avoids the expensive path entirely rather than trying to speed up
the current one) — flagged for whoever next touches Ollama's HTTP layer
directly.

## AFTER — engine-backed (measured 2026-09-18/19, real systemd-managed
`qubi-engine.service`, Unix socket transport, light tier = `qwen3:4b` with
only the `escalate` extension attached per Phase 3's design)

| Point | Measured as | Value |
|---|---|---|
| client connect -> `qubi/session_list` | wall-clock over the real socket | **7ms** |
| `session_list` -> `session/new` result | wall-clock | **59-61ms** |
| cold engine start -> light tier ready | `Engine.start()`'s own timing, direct Ollama warm-up call (Phase 2's fix, not routed through a full ACP turn) | **4.5s** (down from the 54.5s a full-ACP-turn warm-up cost the first time this was tried — see Phase 2's PROGRESS.md entry) |
| first prompt sent -> first token (TTFT), model confirmed warm via `ollama ps` immediately before | wall-clock from `session/prompt` send to first `agent_message_chunk`/`agent_thought_chunk` | **30.9s - 39.4s** across 2 clean runs |

**The honest finding, not softened**: the engine mechanics are a real,
measured win — connect/list/new are all sub-100ms (previously 150-190ms
process-spawn cost, now amortized away entirely since the light tier is
already running) — but **TTFT itself did NOT improve** with the light
tier's minimal one-extension config, and in these two runs was *worse*
than several of the BEFORE baseline's 6-extension runs. This directly
tests (and revises) Phase 0/3's own working hypothesis. Re-reading Phase
0's root-cause evidence: prompt *eval* (prefill, the part tool-schema size
actually affects) was already fast in every BEFORE run too (43ms-1.6s) —
trimming tool schemas from 6 extensions to 1 shrinks an already-cheap
step. The actual TTFT cost is 100% in *generation* (the model's own
extended "thinking" before it answers), which is a property of the model
and prompt content, not the extension list attached to the session. Two
back-to-back AFTER runs against a confirmed-resident model (`ollama ps`
checked immediately before each) both still showed 30-39s TTFT.

**What this means for tonight's design, stated plainly**: Phase 3's
routing/escalation architecture is still the right shape (a light tier
that can hand off to something bigger is valuable regardless), but it
does NOT, by itself, deliver the "<1.5s TTFT docked" latency budget
`gates.json` (Phase 9) sets for the light tier — that gate will fail
tonight, and the reason is now precisely known: `qwen3:4b` reflexively
reasons through hundreds-to-low-thousands of tokens before answering even
a trivial prompt, and `GOOSE_LOCAL_ENABLE_THINKING=false` only partially
suppresses this (confirmed in Phase 0's own A/B: 23.3s -> 17.0s, not to
the sub-2s a genuinely thinking-off request would show). Closing this gap
for real needs one of: (a) a light-tier model that doesn't reason by
default, (b) a way to actually force `think: false` at the Ollama API
level for this model/provider combination (not just the Goose-side env
var, which this session's own probing showed is insufficient), or (c)
accepting that the light tier's real value is background/async use, not
sub-2s interactive latency, and revising the latency gate accordingly.
This is a model-roster/config decision for Liam, not something to
silently patch around tonight — flagged here and in the Phase 9
acceptance results rather than claiming a pass that didn't happen.

**Option (b) confirmed viable, precisely located, not yet wired through**:
tested Ollama's own `think` API parameter directly (bypassing Goose
entirely) against the identical prompt: `think` omitted -> 3654 streamed
chunks, 47.6s total; `"think": false` explicitly set -> **263 chunks,
3.4s total** (a real ~14x reduction, TTFT itself near-identical at
~170-230ms in both cases -- the entire win is generation length, exactly
matching the "1500+ thinking tokens" root cause from Phase 0). This
*works* -- the model genuinely honors `think: false` at the Ollama API
level. The gap is specifically that Goose's `GOOSE_LOCAL_ENABLE_THINKING`
env var does not correctly translate into this API parameter for the
ollama provider (already suspected from Phase 0's A/B showing only a
partial 23.3s -> 17.0s improvement, now confirmed precisely: the real
fix is a ~14x win, not the ~30% Goose's env var actually delivers). This
is the single highest-value follow-up for whoever next touches Goose's
ollama provider integration: find the correct Goose-side config key (if
one exists) that maps to `think: false`, or patch the provider to pass it
through -- not a model swap, not an engine change, a one-parameter fix at
a layer this session doesn't have access to patch (Goose's own Rust
source, not this repo).
